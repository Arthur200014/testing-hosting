# Timeweb App Platform — проверка миграций PostgreSQL (M02-02)

**Назначение:** для существующих `Platform lms` (Timeweb App Platform, Dockerfile `/platform`) и управляемой PostgreSQL. **Не использовать** инструкции для отдельного VPS/Caddy из `docs/deployment/tas-staging.md`: это другой вариант размещения.

## Проверки

| Адрес | Проверяет | Что НЕ проверяет |
|---|---|---|
| `/health/live` | ASP.NET Core отвечает по HTTP | PostgreSQL / таблицы |
| `/health/ready` | соединение с PostgreSQL | EF migrations / структуру таблиц |
| `/health/migrations` | сверяет применённые миграции из `__EFMigrationsHistory` со списком миграций в текущем бинарном API, **только чтение** | наличие всех индексов/колонок при повреждённой ручными изменениями схеме |

В `/health/migrations` ответ `200 Healthy` означает **нет ожидающих миграций для текущей версии API**. `503 Unhealthy` означает, что миграции ожидаются или проверка невозможна; endpoint не выдаёт названия таблиц/SQL/секреты и **ничего не изменяет**.

**После устранения зависания:** запрос истории EF ограничен 4 секундами, а общая проверка — 6 секундами. Если история БД заблокирована или проверка слишком медленная, API должен ответить `503 Unhealthy`, а не держать запрос до тайм-аута прокси. **Наблюдавшийся в Timeweb `502` пока не диагностирован окончательно:** `/health/live` и `/health/ready` пользователь подтвердил как `Healthy`, но эти проверки не читают `__EFMigrationsHistory`. Если после нового деплоя остаётся `502`, искать в логах прокси/приложения ошибку именно запроса к `/health/migrations`. Не выполнять `--migrate` до проверки backup и текущей схемы.

Перед проверкой дождаться успешного нового деплоя, включающего этот маршрут. Старый `404` — ещё не опубликован новый код, не свидетельство повреждения БД.

## Запуск без консоли в Timeweb App Platform

Timeweb App Platform для Dockerfile-приложения может **не предоставлять интерактивную консоль**. Не вводить `dotnet Platform.Api.dll --migrate` в SQL-редактор, поле переменных или Docker build.

Только после подтверждения **готового ручного бэкапа** существующей PostgreSQL:

1. Открыть **App Platform → Platform lms → Настройки → Настройка деплоя → Редактировать → Переменные**.
2. Добавить **локальную** переменную (не глобальную): ключ `TAS_MIGRATE_ON_STARTUP`, значение `apply-20261111120000_TeacherSessions`. Существующую `Database__ConnectionString` не менять.
3. Сохранить настройки и запустить повторный деплой, если он не запустился автоматически.
4. В **Логи приложения** проверить строку `Approved database migrations completed. Remove TAS_MIGRATE_ON_STARTUP.`. Ошибка `Approved migration target does not match...` означает, что схема исходников изменилась: НЕ обходить защиту и не запускать `--migrate` вручную без проверки.
5. Сразу удалить `TAS_MIGRATE_ON_STARTUP` из **локальных переменных**, сохранить и повторно развернуть/перезапустить приложение, чтобы флаг не остался активным.
6. Проверить `/health/live`, `/health/ready`, `/health/migrations`: каждый должен вернуть `Healthy`.

Этот режим **не активен по умолчанию**, не создаёт публичный SQL endpoint, не переносит данные Sheets и не изменяет `EGA/config/manage.html`. Он применяет только одобренный пакет миграций через EF `MigrateAsync()`; если указанная миграция уже применена, режим только сообщает об этом. Пин на `20261111120000_TeacherSessions` запрещает случайно применить новые миграции в следующих версиях бинарного API, даже если переменную забыли убрать. **До бэкапа не включать.** Во время деплоя возможна краткая недоступность API.

## Как проверить на существующем Timeweb

1. Открыть `https://<ваш-технический-домен>/health/live`, `/health/ready`, `/health/migrations`.
2. Если первые два `Healthy`, а третий `Unhealthy`, в БД, скорее всего, отсутствуют некоторые EF migrations. **Не включать automigrate на каждый запуск**. API может отвечать на два простых health endpoints с полностью пустой базой.
3. После проверки состояния и наличия резервной копии выбрать контролируемый способ однократного применения `dotnet Platform.Api.dll --migrate` через работающую консоль Timeweb App Platform (команда существует в `Program.cs`). Запуск создаёт/обновляет таблицы — **не выполнять до backup**, если база уже содержит реальные данные.
4. Повторить все три проверки, затем повторить деплой и убедиться, что health endpoints остаются доступны. В журнал не записывать connection string, JWT и ученические коды.
5. Если консоль Timeweb пустая/недоступна, не добавлять публичный `/migrate` endpoint и не открывать порт PostgreSQL. Миграцию нужно выполнять отдельным защищённым сервисом/задачей с доступом к приватной сети; до этого M02-02 остаётся PARTIAL.

**Известный случай:** `/health/live` в Timeweb был временно отключён как *deploy health-check path*, поскольку платформа ошибочно откатывала работающий контейнер по тайм-ауту. **HTTP endpoint в API продолжает существовать**. Восстановить path в настройках Timeweb только после проверки поведения на контролируемом деплое; факт успешного deploy без этой проверки не равен её прохождению.

**Безопасность:** ранее в чат попала строка подключения PostgreSQL. Пароль необходимо перевыпустить и обновить только в секретных переменных Timeweb, не записывать его в Git. Убедиться, что приватная PostgreSQL не открыта наружу.

**Статус M02-02:** локальная PostgreSQL CI может проверить `/health/migrations`; применение миграций и повторный деплой Timeweb подтверждаются **отдельно** по реальным логам пользователя. **До M03:** backups с проверенным restore (M02-03), согласованные схемы и исходные данные (M03-01).
