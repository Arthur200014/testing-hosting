## 2. Проблемы в активных вкладках

### ДЗ_Назначения — 223 строки

Предварительная проверка required fields, диапазонов, дат, `submittedAt/scorePercent` и ID выявила **10 уникальных строк со структурными проблемами**:

| Строка листа | Проблема | Исправление |
|---:|---|---|
| 23 и 105 | один и тот же `assignmentRecordId` в двух строках; у 105 также отсутствует актуальная ссылка на сочетание `programId+homeworkId` в каталоге | Сверить оба события, сохранить два различных назначения только при подтверждении их самостоятельной идентичности, устранить ошибку каталога; не переименовывать ID наугад |
| 27, 29, 45, 89, 104 | почти пустые фрагменты, нет обязательных ID/сведений о ДЗ/датах/статусе | Установить, был ли факт назначения; если да — восстановить из первичного источника; если нет — удалить/архивировать только после ручного подтверждения |
| 37, 56, 101 | дата сдачи и процентный балл не согласованы: одно поле заполнено без другого | Сверить событие сдачи и восстановить фактическую дату/балл либо убрать ошибочную часть, не выдумывать значение |

**Дополнительно:** строки **6–10** ссылаются на **4 уникальных идентификатора ученика**, которых нет в текущих непустых `Ученики.studentId`. Это **ещё 5 потенциально блокирующих FK-связей**, не входящих в десять структурных строк. Их нельзя пропускать: найти первичные профили, архивные соответствия или официально задокументировать orphan для последующего разрешения. В `ДЗ_Каталог` не найдены пустые ID/program/url; среди текущих catalog keys дублей не обнаружено.

Сравнение с **историческими** 17 проблемными строками `27, 29, 37, 45, 57, 58, 63, 65–74`: проблемы ещё видны у **27, 29, 37, 45**; у остальных 13 повторная предварительная проверка не выявила прежних нарушений. Появились новые проблемные строки `23, 56, 89, 101, 104, 105`. Изменение номеров/состояния по сравнению с прежним XLSX требует нового dry-run штатного импортёра.

**Итого на уровне ограниченной диагностики:** 10 структурных строк + 5 внешних ссылок = **15 различных строк назначений для ручного разбора**. Это **не окончательное** число ошибок импортёра: могут проявиться типы ячеек, исторические semantic conflicts и ограничения PostgreSQL.

### Ученики

Из 35 непустых строк **3 строки (№5, №9 и №14)** не содержат обязательных `studentId`, `studentName`, `inviteCode`, `active`. Осталось **32 строки с непустым studentId**; это не гарантия полного соответствия parser type rules. Дубликатов непустых `studentId` в текущем диапазоне не выявлено. Уточнить: разделители/шаблонные строки или незавершённые профили; не удалять и не создавать код доступа автоматически.

### Другие данные для M03

- `Занятия`: **317 строк и 290 уникальных непустых lessonId**; повтор одного lessonId в нескольких строках соответствует потенциальным нескольким участникам — не удалять «дубли» без сверки `(lessonId,studentId)`.
- `Тесты`: 269 строк. Во всех просмотренных строках отсутствуют `correctCount`, `totalCount`, `startedAt`, `finishedAt` (значения `scorePercent` могут присутствовать). **Legacy importer должен принимать исторические попытки без этих полей**, сохраняя неопределённость; нельзя заполнять нулём.
- `Пробник_Задания`: 419 строк, **53 различных eventId**, одна сдача имеет несколько заданий. У части старых строк нет баллов `earnedPoints/maxPoints` — они не должны трактоваться как нулевые без проверки схемы версии.
- `Пробники`: часть записей не содержит `score`, другие дополнительные поля могут быть необязательными по программе/формату. Различать неоценённые и нулевые результаты.
- `Абонементы`: 31 строка, `resetAt` пустой у 4; история оплаты/сброса требует отдельного ledger в M03-02.
- Во просмотренных `Тесты`, `Пробники`, `Пробник_Сессии`, `Абонементы` не найдено дублей непустых первичных `eventId/sessionId/studentId` в рамках соответствующих одиночных ключей. Это предварительный smoke, не проверка всех составных FK.

## 3. Очередность устранения блокеров

1. **Без записи в источник:** зафиксировать защищённый снимок/экспорт вне Git и его digest; затем провести настоящий `StudentWorkbookParser` и `HomeworkWorkbookParser` dry-run на XLSX без применения. Приложить **только обезличенные diagnostics**.
2. В `Ученики` вручную разобрать строки 5/9/14, затем проверить 4 отсутствующих student ID из назначений строк 6–10 по первичным источникам.
3. В назначениях разобрать 5 неполных фрагментов, 3 неконсистентные сдачи и пару дублей 23/105 с каталогом. **Не пересоздавать историю по предположению**, не ставить фиктивные даты, баллы и статусы.
4. Повторить dry-run с текущим source после исправлений; **zero blocking diagnostics + verified tenant/program map** — предусловие M03 staged apply. Неразрешённые строки хранить в явном quarantine с provenance, но не терять их молча и не считать перенос завершённым.
5. Для тестов/пробников создать version-aware импорт, сохраняющий nullable historical fields. Для уроков и абонементов сверять независимые агрегаты и исходные IDs.

## 4. Границы готовности

- **PASS:** Google Sheets metadata + bounded read всех 20 вкладок, заголовки, объёмы, предварительные FK/required/duplicate/submission diagnostics и безопасный перечень исправлений.
- **NOT_RUN:** фактический `.xlsx` export в этом аудите, ClosedXML `--dry-run`, nullable type/formula validation, сервер, SQL migrations, backup/restore, import `--apply`, любые записи Google Sheets/production.
- **Gate G-M01:** аудит и план устранения готовы; **данные НЕ готовы к M03**. Можно независимо двигаться к `M02-01` (staging сервер), сохранив M03-01 как blocker до подтверждённого нового dry-run.

Следующая задача `M02-01`: приватная PostgreSQL + staging ASP.NET API и секреты вне репозитория; **не подключать manage и не включать production** до успешных следующих gates.
