# Принятые решения TAS

- **D001** 2026-11-11: TAS развиваем **в существующем** `Arthur200014/testing-hosting`, не создаём новый репозиторий. Изоляция по папкам, задача по ID, проверенные коммиты в `main`.
- **D002** Сохраняем проверенные наработки, включая `platform/` (ASP.NET Core + PostgreSQL), `shared/interactive/v1/` и отдельные HTML-интерактивы. Не копируем всё массово и не переключаем production без отдельного безопасного cutover.
- **D003** Целевая архитектура: React/Next.js/TypeScript; ASP.NET Core modular monolith; SignalR; PostgreSQL; Redis по потребности; worker/outbox; заменяемые AI и Telegram/MAX adapters. Это цель, а не заявление, что всё реализовано.
- **D004** Главная продуктовая и научная ценность: проверяемая генерация интерактивных уроков из шаблонов + модель знаний ученика и следующий шаг по существующему банку.
- **D005** Не включаем в ВКР-прототип встроенную видеосвязь, эквайринг и мобильные приложения без новой явной задачи.
- **D006** Перед существенным изменением архитектуры: сопоставить существующий код и решения `docs/architecture/`, записать причину, последствия, план миграции и тесты; не менять стек из-за прихоти очередного чата.
- **D007** Сохраняем корневой `AGENTS.md` как главный источник правил агента и коммитов. TAS-документы — контекст и задачи; они не отменяют проверки и ограничения безопасности.

- **D008** 2026-11-11: Для длинных задач TAS допускаются временные checkpoint-ветки `tas/<TASK_ID>` с небольшими WIP-коммитами, чтобы код и ход работы переживали смену чата. `main` получает только проверенный итог; активная ветка записывается в HANDOFF на `main`.

- **D009** 2026-11-11: Для каждой TAS-roadmap задачи перед изменением исполняемого кода обязательно создавать/обновлять карточку `.ai/tasks/tas-Pxx-yy.md` по шаблону `.ai/tas/TASK_TEMPLATE.md`. Сначала точечный аудит и план с чеклистом, затем подтверждённый GitHub planning commit, только затем реализация. Длинные задачи начинают с checkpoint-планирования в `tas/<TASK_ID>`.

- **D010** 2026-11-11: Для каждой изменяемой функции TAS тесты являются частью **той же** задачи. В карточке заранее описываются позитивные, негативные, граничные и релевантные регрессионные кейсы. После реализации тесты запускаются реально на доступной изолированной среде или в GitHub Actions для конкретного SHA; FAIL -> исправление -> повтор, NOT_RUN -> BLOCKED. Глобальный прогон всех страниц не нужен без зависимости по коду. Чисто документальные задачи проверяются документальными критериями.

- **D011** 2026-11-11: TASK CI использует выбор изменённых файлов и запускается на task-ветках `tas/**`; изменения самого CI не должны прогонять весь legacy-репозиторий. Граничные условия: отсутствие обязательного task test — FAIL; при известной старой ошибке за пределами текущей задачи не менять чужой код ради зелёной галочки. Для frontend, когда он появится, нужны реальный test+typecheck/build scripts; backend остаётся на изолированном Docker/PostgreSQL. Полный P03-04 не закрывается одним bootstrap.

- **D012** 2026-11-11: Более поздний `AGENTS.md` (разделы Implementation, Proportionate verification, Git and continuation) **заменяет процессуальные требования D009/D010** об обязательных карточках, предварительном planning commit, полном наборе четырёх кейсов для любой задачи и автоматическом BLOCKED при NOT_RUN. Карточка и регрессионные тесты нужны по фактическому риску; для high-risk/auth/backend сохраняются строгая проверка и task branch при отсутствии верификации. D009/D010 остаются историческим контекстом, но не актуальными обязательными правилами.

- **D013** 2026-11-11: По явному решению владельца **меняем порядок реализации**. Новый действующий маршрут — `M01 → M02 → M03 → M04 → M05 → M06 → M07`: schema/tenant/auth → staging server/PG → полный импорт Sheets → защищённый teacher API + текущий `EGA/config/manage.html` → контролируемый production cutover → новая универсальная админка → интерактивы/AI. Прежние Pxx задачи и результаты не аннулируются, но прежний порядок и `P02-05` как NEXT_ACTION отменены. Исходный Pxx roadmap сохранён в `TASK_BOARD_LEGACY.md`.
- **D014** 2026-11-11: **Multi-tenant, multi-subject by design.** Один преподаватель/организация не должен получать чужих учеников и результаты. Предмет не привязывается к ЕГЭ/ОГЭ; programme/subject configurable, история сохраняет владельца. `manage` — временный главный UI, а новая админка строится позднее поверх того же ASP.NET API.
- **D015** 2026-11-11: Действующий Google Sheets/GAS остаётся production source of truth до: валидации исходника, complete rehearsal, teacher auth и tenant checks, staging/prod backup+restore, финальной дельты и отдельного явного одобрения на cutover. Запрещён silent dual-write и выдача приватного teacher package без настоящей авторизации; не угадывать пустые значения миграции.
