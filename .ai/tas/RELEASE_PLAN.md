## Изменение направления

Владелец выбрал максимально точное воспроизведение доступного кабинета преподавателя Meleto в **существующем TAS**. Начать с классов и основного интерфейса. Ранее сформулированные M01–M07 и «три результата до релиза» сохраняются как история; они **не определяют** NEXT_ACTION. Предыдущий отдельный `platform/teacher.html`, ASP.NET Core и PostgreSQL уже существуют. Прежняя `EGA/config/manage.html`/GAS остаётся действующей там, где ещё используется. Не повторять импорт; не менять данные, пароли и доски в живой системе.

Новый дизайн не требует автоматического переключения writer с GAS на PostgreSQL. Не смешивать перенос данных, переделку UI и production cutover. Работа над новым кабинетом может идти поверх существующего API и добавленных совместимых endpoints/миграций. Перед любым переключением действующего writer, реальным восстановлением БД или изменением живых записей нужен отдельный явный запрос владельца.

Парные уроки моделируются одним занятием с несколькими участниками. Синтетические backend/PostgreSQL/Chromium проверки прежнего кабинета проходили. Это **не** означает готовый Meleto UI и **не** подтверждает каждый живой сценарий.

**Не установлено по коду:** есть ли подходящая сущность «класс» в полном смысле Meleto (не равнять автоматически с `LearningProgram`), расписание как правило, темы, чат, файлы, доски и платежи новой платформы. Проверять только нужные модели, миграции, маршруты и страницы перед задачей. Не отмечать этап DONE по одному похожему названию.

**Операционный долг предыдущего релиза:** status managed Timeweb backup/retention, running deployment revision, авторизованная задержка API и live submit/grade не подтверждены независимо. Держать это в `RELEASE_SAFETY` ниже; оно не возвращает старый roadmap и не блокирует безопасную работу над UI. Production restore и изменения реальных учеников не проводить.

## Очередь реализаций

Этап завершается работающим сценарием: реальная модель/endpoint → интерфейс → сохранение/отмена/ошибки → проверка доступа и сопоставление с PNG. При долгой работе вести одну активную ветку и один `NEXT_STEP`. Конкретная следующая задача всегда только в HANDOFF.

| Этап | Сценарий и экраны референса | Итог |
|---|---|---|
| **UI-01** | Каркас кабинета, навигация, список классов `01`; выбор формата `02` | Существующий вход учителя открывает новый каркас, список питается данными своего workspace, действия ведут к настоящим сценариям; базовая визуальная сверка |
| **UI-02** | Создание/карточка/настройки класса `03–06, 09–10`, редактирование/архив/статистика `31–33` | Индивидуальные/групповые классы, участники, настройки, отмена и сохранение через API, без переноса/удаления исторических учеников |
| **UI-03** | Занятие/расписание/календарь `07–08, 11–15, 23–26, 37–41, 73–74` | Правило расписания отдельно от конкретного урока; разовый/массовый урок; карточка и посещения; календарь день/неделя/месяц |
| **UI-04** | Программа, задания, материалы и библиотека `16–18, 27–29, 34–36, 48–50, 72` | Темы и вложения переиспользуются; шаблон задания отделён от назначений и сдач; файлы/ссылки/записи работают в рамках доступа |
| **UI-05** | Состав класса/приглашения/ученики `20–22, 42–47` | Карточка ученика и вкладки, связи с классом, приглашения, результаты/отчёт; чужие ученики недоступны |
| **UI-06** | Доски и чат `51–52, 64–69` | Доска с доступом, сохранением и восстановлением; сообщения привязаны к участникам и контексту |
| **UI-07** | Оплата обучения, профиль, роли, подписка `19, 30, 53–63, 70` | Счета/платежи учеников отделены от тарифа платформы; настройки и роли подтверждены сервером; внешние платежи не имитировать |
| **UI-08** | Публичная страница `71` и сквозная доводка | Публичный экран, responsive поведение, доступность, согласованность всех переходов и единая визуальная проверка |

Номера отражают кадры, **не** нумерацию задач и не исчерпывающие возможности сервиса. Подробная однозначная привязка всех 74 PNG — в индексе. Этапы UI-01 и UI-02 — первоочередные; после них переходить по таблице. Уточнять очередность внутри этапа по фактическим зависимостям.

## Общая техническая модель (целевая, уточняется по коду)

`Workspace / TeacherUser / Membership` владеют данными. «Класс» — отдельный долговременный контекст обучения с типом и настройками; `Enrollment` связывает учеников с классом. `ScheduleRule` задаёт повторы и часовой пояс; `Lesson` — экземпляр занятия; `LessonParticipant` — независимое посещение ученика. `Topic` связывается с уроками; `Assignment`, назначения конкретным ученикам, `Submission` и проверка — разные сущности. `Material`/файл с контекстной связью не дублирует бинарник. `Board`, права и ревизии, `Conversation`/`Message`, приглашение/связь представителя, `Invoice`/`Payment` и тариф учителя — отдельные модули.

Это **не требование сразу создать десятки таблиц**. В каждом этапе использовать существующие модели, затем добавить минимальные совместимые сущности с tenant-проверкой на сервере, миграцией и тестами только затронутого поведения. Не объявлять предметно нейтральный `LearningProgram` эквивалентом класса без проверки его инвариантов и связей. Отношения и переходы описаны в `BUILD_PROMPT_RU.md` архива.

## Готовность этапа и передача в новый чат

Для завершённого сценария нужны: ID кадра и сравнение на viewport около 1360 × 930; навигация, сохранение/отмена/валидация/ошибки и пустое состояние; нужные данные своего workspace после перезагрузки; отсутствие доступа к чужому; статус тестов `PASS / FAIL / NOT_RUN`. Для CSS не создавать формальные тесты; для API/auth/миграции — целевые проверки на синтетических данных. Невыполненные интеграции описывать честно.

После каждого существенного шага обновлять короткий HANDOFF: активный этап, ветка/коммит, конкретный следующий шаг и реальные проверки. Обновлять чеклист при принятом сценарии, а не каждый микрокоммит. Следующий чат начинает с HANDOFF, а не с повторного аудита всего репозитория.
