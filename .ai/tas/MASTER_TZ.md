# TEACHER AI STUDENT — устойчивое техническое задание

**Версия:** 2026-11-14. Это продуктовые инварианты, **не очередь задач**. Приоритет, этапы и текущий шаг — в [RELEASE_PLAN.md](./RELEASE_PLAN.md), [PHASE_CHECKLISTS.md](./PHASE_CHECKLISTS.md) и [HANDOFF.md](./HANDOFF.md). Исторические Pxx/Mxx планы и прежнее полное ТЗ сохранены в [MASTER_TZ_LEGACY.md](./MASTER_TZ_LEGACY.md).

## Продукт

TAS — платформа для преподавателя/небольшой школы с учениками, классами, расписанием, занятиями, ДЗ, результатами, материалами, доской, чатом и расчётами. Пилот — математика ЕГЭ/ОГЭ, модель должна допускать другие предметы и независимых преподавателей. Владелец 14 ноября выбрал первым приоритетом максимально точный доступный кабинет преподавателя Meleto; свои особые возможности позже. [Пакет референсов](./MELETO_REFERENCE.md) показывает 74 состояния, но не раскрывает исходную БД или все скрытые сценарии.

## Имеющаяся основа

Репозиторий уже содержит `platform/teacher.html` и `platform/student.html`, ASP.NET Core API, PostgreSQL модели/миграции, вход преподавателя, данные учеников/уроков/ДЗ/абонементов и отдельные образовательные `EGA/`/`OGA/` страницы. Импорт ранее подтверждён владельцем. Старый `EGA/config/manage.html` и GAS могут ещё участвовать в рабочем контуре. Следующая задача сверяет существующий код с нужным экраном; не создаёт второй проект.

## Системные инварианты

- У каждого API чтения и записи — проверка живой teacher session, роли и принадлежности workspace; переданный из браузера ID недостаточен. Чужие ученики, задания и доски недоступны.
- Один урок может иметь нескольких участников и независимые посещения. Изменение расписания не переписывает проведённые занятия; повторное массовое планирование не создаёт дублей.
- Класс/курс, правило расписания и конкретное занятие — разные понятия. Если существующая модель их совмещает, расширение должно сохранять старые связи.
- Каталог задания, назначения конкретным ученикам, попытка сдачи и проверка различаются. Отчёты строятся из фактических событий; отсутствие данных не превращается в 0. Сохранены согласованные правила отчётов (последние 8 занятий и вес ДЗ/тестов 80/20), пока пользователь не изменит их.
- Абонементы/балансы и платежи корректируются по фактам, без выдуманных сумм. Учебные счета отличаются от подписки самого преподавателя на платформу. Повтор операции не должен списывать занятие дважды.
- Нельзя терять живые данные при развитии схемы. Не удалять учеников/доски, не менять пароли и не повторять импорт как побочное действие переделки интерфейса.
- Не запускать production restore и не менять writer с GAS на PostgreSQL без отдельного решения и проверенного плана сверки/отката. Избегать двух незаметных источников записи.

## Архитектура и реализация

Использовать существующий ASP.NET Core/PostgreSQL и доступные браузерные модули, совместимые миграции и синтетические данные для проверки. React/Next.js, SignalR, Redis, объектное хранилище, worker/AI/мессенджеры — ранее обсуждённые варианты развития, **не обязательный новый стек для UI-01**. Если потребуются, сначала обосновать их на конкретном сценарии и миграции.

Новый кабинет повторяет визуальное расположение и переходы референса, но получает данные из TAS. Для каждого сценария: точный ID PNG → аудит имеющегося API/моделей → минимальная реализация → существенные успешные/ошибочные/чужие tenant пути → сравнение desktop с PNG → commit и короткий HANDOFF. Невыполненная интеграция и неизученный экран помечаются явно. Не объявлять весь продукт готовым по статическому сходству.

## Отложенное развитие

Интерактивные уроки и проверяемая AI генерация, рекомендации на основе реальных результатов, мессенджеры и расширенный кабинет ученика/родителя сохраняются как видение продукта. Старый [исторический документ](./MASTER_TZ_LEGACY.md) содержит их подробности, но не может переопределять текущий UI план.
